# CallTag 플랫폼 현황·Google 로그인·결제·데이터 보안 로드맵

최종 갱신: 2026-08-05

이 문서는 CallTag Android 앱과 PageRo/inlet 서버의 현재 구현 상태, 정식 출시 전에 필요한 Google 로그인·결제·데이터 동기화·보안 작업, 운영 활성화 조건을 하나의 기준으로 고정한다.

## 1. 현재 완료된 범위

### Android 앱

- 통화 종료 후 고객 정리 화면과 통화기록 지연 감지
- 화면 표시 실패 시 재시도와 알림 fallback
- 고객·상담·메모·후속 일정 로컬 SQLite 저장
- 문자 템플릿, 자동문자, 부재중·통화 후·후속 예약 설정
- 후속문자 1·3·5·7일 또는 1~30일 직접 선택
- 템플릿 선택 버튼 상시 노출
- 암호화 `.ctbackup` 수동 백업·복원
- 이용권 화면, 무료 3일, 추천인 등록 시 +5일
- Google Play 미등록 준비 모드와 구매 선행 차단
- 추천인 코드·추천 현황 화면

### 서버

- 이메일·비밀번호 계정과 이메일 인증
- 서명된 세션 토큰과 계정 상태·세션 버전 검증
- PageRo 문의 수집과 CallTag 가져오기
- 기본 무료 3일·추천 +5일 이용권
- Google Play 구독 검증·복원 코드와 출시 전 비활성 게이트
- 웹·Play 중복 결제 사전 판정
- 추천인 코드 자동 생성과 추천 귀속
- D1 기반 결제·추천 데이터

## 2. 현재 구조의 핵심 부족점

### 앱 삭제·기기 변경

현재 고객·상담·메모·일정·문자·템플릿 데이터의 정본은 휴대폰 내부 DB다. Android 자동백업은 비활성화되어 있으므로 앱 삭제, 저장공간 데이터 삭제, 휴대폰 초기화, 기기 분실 시 수동 `.ctbackup` 파일이 없으면 복구할 수 없다.

### 서버 저장 부재

서버에는 계정·결제·추천·PageRo 원본 문의가 남지만 CallTag에서 가공한 고객 메모, 상담 상태, 통화 후 기록, 후속 일정, 템플릿과 자동문자 설정은 계정 단위로 동기화되지 않는다.

### 인증

현재 Google 로그인은 정식 서버 검증 방식으로 완료되지 않았다. 정식 출시 전에는 Android Credential Manager 또는 Google Identity Services에서 받은 ID Token을 서버가 Google 공개키로 검증하고, `sub`를 외부 식별자로 저장해야 한다. 이메일 주소만으로 기존 계정을 자동 병합하면 계정 탈취 위험이 있으므로 검증된 이메일과 명시적 계정 연결 절차가 필요하다.

### 결제

Google Play Console 앱·구독 상품 등록, 라이선스 테스터, 서비스 계정 연결, RTDN, 내부 테스트 구매·갱신·취소·유예·환불 검증이 남아 있다. 웹 결제는 사전 판정까지만 있으며 checkout, 결제 webhook, 환불·취소·중복처리 방지, 영수증과 부가세 처리가 없다.

### 운영 보안

핵심 고객 데이터를 서버에 저장하려면 단순 D1 저장만으로는 부족하다. 계정 격리, 애플리케이션 레벨 암호화, 전화번호 검색용 HMAC, 세션·기기 관리, 대량조회 제한, 민감정보 로그 금지, 감사기록, 삭제·보관 정책이 필요하다.

## 3. 확정 데이터 원칙

### 서버 동기화 대상

- 고객 이름·전화번호·메모·상태
- 통화 후 작성한 상담 기록
- 후속 할 일과 일정
- 문자 템플릿과 자동문자 설정
- 문자 발송 결과의 최소 메타데이터

### 기본적으로 서버에 올리지 않는 데이터

- 통화 녹음
- 휴대폰 전체 연락처
- CallTag와 무관한 전체 통화기록
- 기본 문자 앱의 전체 수신·발신 내용
- 클립보드, 위치, 광고식별자
- 로그인 세션·구매 토큰 원문

### 정본과 복구

- 앱 로컬 DB는 빠른 사용과 오프라인 작업을 위한 1차 저장소다.
- 서버는 계정별 암호화 복구본과 기기 간 동기화 정본 역할을 한다.
- 사용자가 앱을 삭제하고 같은 계정으로 로그인하면 서버에서 데이터를 복구한다.
- 수동 `.ctbackup`은 서버 장애·계정 복구 실패에 대비한 보조 수단으로 유지한다.

## 4. 보안 설계 기준

### 계정 격리

- 모든 서버 레코드에 `owner_id`를 저장한다.
- `owner_id`는 요청 본문에서 받지 않고 검증된 세션에서 서버가 결정한다.
- 모든 SELECT·UPDATE·DELETE 조건에 `owner_id`를 포함한다.
- 관리자용 원문 조회 API를 만들지 않는다.

### 민감정보 암호화

- 고객 이름, 전화번호, 메모, 상담 내용은 AES-256-GCM으로 애플리케이션 레벨 암호화한다.
- 암호화 키는 Cloudflare secret으로만 보관하며 저장소·로그·API 응답에 넣지 않는다.
- 레코드별 무작위 IV와 AAD(`owner/entity/id/version`)를 사용한다.
- 전화번호 중복검색은 원문 인덱스 대신 별도 HMAC-SHA-256 검색값을 사용한다.
- 암호화 키 버전을 저장해 향후 키 교체가 가능해야 한다.

### 세션과 기기

- Google ID Token은 앱에서 신뢰하지 않고 서버에서 `iss`, `aud`, `exp`, `sub`, 이메일 검증 여부를 확인한다.
- 앱 세션은 단기 access token과 회전 가능한 refresh token 구조로 전환한다.
- 기기별 식별자는 원문을 저장하지 않고 HMAC으로 저장한다.
- 사용자는 다른 기기 세션을 확인하고 원격 해제할 수 있어야 한다.

### API 방어

- 동기화 push·pull은 한 요청 최대 100건으로 제한한다.
- 응답 페이지 크기와 본문 크기를 제한한다.
- 계정·기기별 rate limit을 적용한다.
- 오래된 version이 최신 데이터를 덮지 못하도록 낙관적 버전 검사를 한다.
- 삭제도 tombstone으로 동기화한 뒤 보관기간 종료 후 물리 삭제한다.
- 반복 실패, 대량 조회, 다른 owner 접근 시도를 보안 이벤트로 기록한다.

### 로그와 운영

- 전화번호·이름·메모·문자 내용·세션 토큰은 로그에 남기지 않는다.
- 보안 로그에는 이벤트 종류, 시간, 익명화된 계정·기기 식별자, 결과 코드만 기록한다.
- Cloudflare·GitHub·운영 이메일에 MFA를 적용한다.
- 운영 DB를 개발 환경으로 복제하지 않는다.
- 데이터 접근용 긴 수명의 공용 관리자 토큰을 만들지 않는다.

## 8. 운영 활성화 조건

동기화 API는 다음 조건을 모두 만족하기 전까지 비활성화한다.

- `CALLTAG_SECURE_SYNC_ENABLED=1`
- `CALLTAG_DATA_ENCRYPTION_KEY` 32바이트 secret 설정
- `CALLTAG_DATA_SEARCH_KEY` 별도 secret 설정
- D1 migration 적용
- 계약 QA·production build 성공
- staging에서 계정 간 격리 테스트
- 삭제·재설치 복구 테스트
- 키가 로그와 응답에 노출되지 않는지 확인

## 9. 금지사항

- 클라이언트가 보낸 `owner_id` 사용
- 고객 전화번호·메모 평문 저장
- 암호화 키를 `wrangler.jsonc`에 기록

- 전체 연락처 자동 업로드
