광고 전환수와 실제 문의가 다른 이유: 랜딩페이지 지표 검증 가이드

광고 관리자에 ‘전환 20건’이라고 보여도 실제 상담 가능한 문의는 12건일 수 있습니다. 광고 성과 수치와 영업 접수 건수는 같은 사건을 다른 방식으로 셀 수 있기 때문입니다. 이 글은 광고 플랫폼의 자동 최적화 수치가 아니라 실제 원본 이벤트를 확인하는 방법을 다룹니다.

먼저 네 가지 숫자의 분모부터 분리합니다

이벤트무엇을 뜻하나중복되기 쉬운 경우확인 기록

페이지 방문랜딩페이지에 도달한 방문 또는 세션재방문, 로딩 오류, 동의 설정 차이분석도구 세션·페이지뷰

광고 전환수와 접수함 신청 수가 다를 때

  1. 같은 기간과 같은 시간대를 비교합니다. 광고 플랫폼과 접수 서버가 날짜 경계를 다르게 잡으면 하루 차이가 납니다.
  2. 접수 완료 시점을 정의합니다. 제출 버튼 클릭은 성공이 아닙니다. 서버에서 접수번호를 반환한 다음에야 문의 성공 이벤트를 보내는 것이 안전합니다.
  3. 완료화면을 새로고침할 때 전환 이벤트가 재발송되는지 확인합니다. 전환 중복 방지를 위해 요청 식별자를 기록할 수 있습니다.
  4. 광고 태그가 이중 설치됐는지 확인합니다. 코드 직접 설치와 태그 매니저가 같은 이벤트를 보내는 경우가 있습니다.
  5. 브라우저·광고 차단·동의 상태별로 실제 서버 접수와 분석 이벤트의 차이를 구분합니다.
  6. 스팸·중복·테스트 문의를 제외한 유효 문의 수도 별도 기록합니다.

모두 가상 데이터인 계산 예시

광고비 600,000원, 광고 클릭 1,000회, 페이지 방문 800회, 서버 접수 40건, 유효 문의 30건, 계약 3건이라고 가정합니다. 실제 페이지로 이용자의 운영 데이터가 아닙니다.

‘광고 전환당 비용’만 비교하면 접수 품질이 다르다는 사실을 놓치기 쉽습니다. 광고 클릭→방문→서버 접수→유효 문의→계약을 동일한 기준 기간으로 나눠 살펴보면, 광고 클릭 자체가 부족한지, 폼에서 이탈하는지, 유효하지 않은 문의가 많은지 구별할 수 있습니다.

실제 운영에서 꼭 남겨야 하는 최소 기록

  • 접수 ID, 접수 성공 시각, 페이지 ID, 광고 유입 채널(동의·법적 근거가 충족된 경우)
  • 중복 판단 기준과 테스트 접수 여부
  • 문의 처리 상태 및 계약 여부를 구분하는 값
  • 실패 상태 코드와 요청 재시도 여부. 실패한 요청을 성공으로 집계하면 안 됩니다
운영상 주의

개인정보를 광고 분석 이벤트에 그대로 전송하지 마세요. 전화번호·이메일 같은 식별자는 목적과 적절한 보호조치를 먼저 검토해야 합니다. 사이트 운영 로그 역시 개인정보 처리방침과 보관기간을 준수해야 합니다.
